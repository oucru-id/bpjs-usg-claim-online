# Deployment with username and password

This version does not use Google OAuth for staff login. The web app still executes as the deploying administrator so the database Spreadsheet and Drive folders remain private.

## 1. Replace the Apps Script files

Copy all current files from `src/` to the Apps Script project.

Important:

- add `PasswordAuthService.gs`;
- add `ClaimService.gs` and `DriveService.gs`;
- add `DocumentService.gs`, `TokenService.gs`, and `VendorQrCode.html`;
- add `GcsService.gs` and copy `appsscript.json` so the pinned OAuth2 library dependency is included;
- add `PdfService.gs`;
- add `BackupService.gs`;
- add `OrthancBridgeService.gs`;
- delete the old `OAuthService.gs` from Apps Script;
- replace every other `.gs` and `.html` file;
- replace `appsscript.json`.

Enable **Project Settings → Show appsscript.json manifest file in editor** if the manifest is hidden.

## 2. Run the migration

Save all files, select `setupApplication`, and click **Run**.

Setup adds the `AUTH_CREDENTIALS` sheet and these Script Properties automatically:

```text
AUTH_MODE=USERNAME_PASSWORD
PASSWORD_PEPPER=<random secret generated by setup>
PASSWORD_HASH_ITERATIONS=12000
LOGIN_MAX_ATTEMPTS=5
LOGIN_LOCK_MINUTES=15
APP_SESSION_HOURS=8
```

Never delete or change `PASSWORD_PEPPER` after passwords have been created; doing so invalidates every password. Setup revokes sessions created by the previous authentication version. The obsolete `AUTH_IDENTITIES` sheet may remain but is no longer read.

For an existing installation, setup also adds the `must_change_password` column to `AUTH_CREDENTIALS`. If recognized columns are in an older order, setup safely rewrites them into the current order while preserving the values in every row. If an unknown, blank, or duplicate header exists, setup stops without modifying that sheet so the header can be reviewed manually.

If a recognized new column already contains data but its header is blank, setup repairs the header only when its position maps unambiguously to the expected column. Ambiguous blank columns still fail closed without changing data.

The manifest requests Google Documents access for PDF composition and external-request access to initiate Google Drive resumable uploads for original DICOM files. Review and approve both when Google prompts the deploying administrator.

Version 6.1 adds raw-backup status columns to `ORTHANC_DICOMS` and copies every original DICOM to the second Drive independently of claim creation. Existing data is preserved.

Version 6.3 adds `patient_phone` to `CLAIMS`. Existing claim rows are preserved and receive an empty value; enter a No. HP before editing and saving an older claim.

Version 6.5 adds anonymous deterministic `F1` storage filenames plus private logical-name and Drive-URL mappings. Version 6.7 adds PDF/JPEG/PNG supporting-file selection and converts each PDF page to JPEG in the browser. Version 6.8 reads both DICOM `PatientID` and `PatientComments`, detects a unique 16-digit NIK and doctor-name candidate, and warns instead of guessing when values conflict. Version 6.9 adds `doctor_name` to `CLAIMS` and allows any authenticated user with access to a completed claim to reopen it. Version 6.9.1 also allows data edits on every non-archived claim; editing a Ready/PDF-generated/Completed claim automatically returns it to Collecting Documents so the PDF must be regenerated. Version 6.9.2 detects and repairs claim rows whose doctor/date/status values were shifted because the new source wrote before the `CLAIMS` schema migration, and blocks subsequent writes when a sheet schema is stale. Existing unaffected claim rows are preserved and receive an empty doctor name; fill it before creating a new PDF for an older claim. The current release does not use Cloud KMS/E1, `FILENAME_KMS_KEY_NAME`, `FilenameCryptoService.gs`, or the `cloud-platform` OAuth scope.

Version 6.10 adds automatic delivery of each newly generated PDF version to a separate private verifier Drive folder, with status metadata in `CLAIMS` and no verifier URL exposed to staff. Version 6.10.1 changes only the verifier copy to a readable logical filename; primary and backup copies remain anonymous.

Version 6.10.2 locks completed claim data in both the browser and server. **Edit Data Klaim** becomes available only after **Buka Kembali Klaim** changes the status to Collecting Documents.

Version 6.11 changes only the verifier copy: it uses `KLAIM_USG_PKM_<PUSKESMAS>_<YYYYMMDD>_<NAMA_PASIEN>_<NIK>_DR_<NAMA_DOKTER>.pdf`, places it directly in a folder such as `OKTOBER 2026` below the configured verifier parent based on the examination date, and keeps only the latest tracked verifier copy for each claim. No intermediate `KLAIM` folder is created. Primary and backup naming and primary PDF version history are unchanged.

Version 7.0 adds dual OrthancBridge destinations and GCS PDF delivery. Python can send DICOM/JPEG to GCS independently of its existing web app/Drive path. Apps Script sends the reviewed anonymous `F1` PDF to GCS when **Selesaikan Klaim** is confirmed. Follow [GCS_DUAL_DELIVERY.md](GCS_DUAL_DELIVERY.md); never add a credential JSON file to `src` or Git.

Version 7.1 adds the in-app WhatsApp console. It reads the bridge-scoped study list and delivery outbox from BigQuery, serves private GCS JPEG previews only through an authorized backend call, and sends manual requests to the production n8n webhook with a stable `delivery_reference_id`. Follow [BIGQUERY_DICOM_REGISTRY.md](BIGQUERY_DICOM_REGISTRY.md); leave `ENABLE_WHATSAPP_DELIVERY=false` until the outbox table, IAM, webhook authentication, and status updates have passed fictitious-data testing.

Version 7.2 adds explicit per-photo selection. Before deploying it, add `selected_object_keys ARRAY<STRING>` to `whatsapp_deliveries` using the migration in `orthanc-bridge/bigquery_schema.sql`, and update n8n so manual requests query only the `selected_object_keys` supplied in the webhook. Do not deploy the UI first while n8n still queries every JPEG by `study_key`.

After a successful migration, the application header should display `7.2.0-whatsapp-photo-selection`. The setup result includes `repairedClaimDoctorRows`; if it is greater than zero, review those repaired claims before resuming normal work.

After deployment, log in as administrator, open **Sistem**, and run **Jalankan Diagnostik**. The server-side self-test function requires an application session token and is not intended to be run directly from the Apps Script editor.

## 3. Redeploy

1. Open **Deploy → Manage deployments**.
2. Edit the existing web-app deployment.
3. Select **New version**.
4. Keep **Execute as: Me**.
5. Set access to **Anyone**. Some interfaces describe this as anyone with the link.
6. Deploy and retain the production `/exec` URL.

The page is publicly reachable, but it returns no patient or account data until a valid application session is supplied. Every protected server function authorizes the session independently.

The `/exec` deployment also accepts authenticated outbound requests from OrthancBridge. Bridge reception remains disabled until an administrator generates a connection key. Continue with [ORTHANC_BRIDGE.md](ORTHANC_BRIDGE.md) only after the normal claim workflow passes its tests.

## 4. Create usernames and temporary passwords

Open `/exec` using the same Google account that owns/deploys the script. The installer administrator can enter without a password only to bootstrap account management.

1. Open **Pengguna**.
2. Edit each existing user.
3. Enter a unique username using 4-64 lowercase letters, numbers, dots, underscores, or hyphens.
4. Leave the password fields blank to use the default initial password `admin123`. If you enter a different temporary password, it must contain 6-128 characters.
5. Save. The account is marked as requiring a password change.
6. Finally, create a username for the Administrator account. This disables the installer-only bypass; the application will then require username/password login for everyone.

Examples of valid usernames:

```text
admin.bpjs
heri01
bidan_narmada
```

Do not reuse personal email, banking, or Google passwords.

## 5. Test staff login

1. Open the `/exec` URL in an incognito/private window.
2. Enter the staff username and `admin123` (or the temporary password entered by the administrator).
3. Confirm the application shows **Ganti Kata Sandi** instead of the dashboard.
4. Enter and confirm a new password of at least 6 characters. The new password cannot be `admin123`.
5. Confirm the dashboard loads without the Pengguna or Sistem admin menus.
6. Click **Keluar** and confirm the session is rejected afterward.
7. Enter an incorrect password five times and confirm login is temporarily blocked for 15 minutes.
8. Confirm the staff user still cannot open the private Spreadsheet or Drive folder.

Any password reset performed from **Pengguna** is temporary and forces the user through the same password-change screen.

### Recover a forgotten installer-administrator password

If the administrator account tied to `ADMIN_EMAIL` cannot log in, do not change `PASSWORD_PEPPER`, edit the password hash manually, or create a public reset endpoint.

1. Open the Apps Script project while signed in as the Google account recorded in `ADMIN_EMAIL`.
2. Select `resetAdminPassword` in the function list and click **Run**.
3. Confirm the execution result reports `success: true` and note the returned administrator username.
4. Open the production `/exec` URL in an incognito/private window and sign in with that username and the temporary password `admin123`.
5. Create a different password when the mandatory password-change screen appears.

The recovery function verifies the active Google identity and resets only the configured installer administrator. If `AUTH_CREDENTIALS` does not yet contain that administrator, the function creates a unique username (normally `admin`) and returns it. It also clears any login lock, revokes all existing sessions for that administrator, stores only a newly salted and peppered hash, and writes `ADMIN_PASSWORD_RESET` to `AUDIT_LOG`.

## 6. Test user deletion

1. Create a temporary staff account that has never created or edited a claim or document.
2. Click **Hapus**, cancel once, and confirm the account remains.
3. Click **Hapus** again and confirm deletion.
4. Confirm the deleted username can no longer log in.
5. Confirm there is no **Hapus** button for your own current administrator account.
6. For a user referenced by claim or document history, confirm deletion is blocked and deactivate the account instead.

## 7. Test claim management

Use clearly fictitious data only, for example `Pasien Demo`, NIK `0000000000000000`, No. HP `081234567890`, and doctor `dr. Demo`.

1. Log in as STAFF and confirm all interface labels are in Bahasa Indonesia.
2. Click **+ Buat Klaim Baru**, enter the demo patient data and **Nama Dokter**, and save.
3. Confirm the generated code follows `CLAIM-YYYYMMDD-XXXXXX` and contains no patient name, NIK, No. HP, or doctor name.
4. Confirm the list displays the complete patient name, NIK, normalized No. HP, and doctor name for an authorized user.
5. Open the claim and confirm the authorized detail displays the complete 16-digit NIK, No. HP, and doctor name.
6. Edit it and select **Mulai Pengumpulan Berkas**.
7. Confirm a private folder named only with the claim code exists below the configured `CLAIMS` folder and contains the standard subfolders.
8. With a staff account from another facility, confirm the claim is not visible unless **Lihat semua klaim** was explicitly granted.
9. Log in as ADMIN, archive the demo claim, and confirm it disappears from the active list.
10. Enable **Sertakan arsip** and confirm the archived claim is searchable.
11. Review `AUDIT_LOG` for `CLAIM_CREATED`, `CLAIM_UPDATED`, `CLAIM_COLLECTION_STARTED`, and `CLAIM_ARCHIVED`.

## 8. Test image and supporting-document upload

Use only fictitious documents during this test.

1. Open a non-archived demo claim and upload two JPEG/PNG USG images from a computer.
2. Confirm both thumbnails appear and the Drive filenames contain only the document type and UUID.
3. Upload the same image again and confirm the duplicate warning appears.
4. Open the normal `/exec` URL on a phone and log in with an authorized application account.
5. Select the demo claim from **Daftar Klaim USG** and verify the patient, examination date, and facility.
6. From **Unggah Berkas Pendukung**, choose a PDF or JPEG/PNG photo for KTP, Buku KIA, and SPP/FKPP BPJS, waiting for each success message. Confirm that the picker does not open the camera automatically.
7. Upload one fictitious multi-page PDF. Confirm each page becomes a separate JPEG document in the original page order.
8. Confirm a PDF larger than 25 MB and a PDF with more than 20 pages are rejected with a clear message.
9. In the `DOCUMENTS` sheet, confirm each new supporting photo or rendered PDF page is at most 1280 x 720 in landscape or 720 x 1280 in portrait. Confirm its aspect ratio is not stretched.
10. Click **Perbarui Daftar** on the computer and confirm the new thumbnails appear.
11. Use **Lihat**, then delete one fictitious document and confirm it disappears while its `DOCUMENTS` row remains with `deleted_flag=TRUE`.
12. Confirm another-facility staff account cannot find the claim or retrieve its thumbnails.
13. Repeat the PDF selection on a real phone using the clinic network. If the PDF component fails to load, verify access to `cdnjs.cloudflare.com` and retry.
14. Review `AUDIT_LOG` for `DOCUMENT_UPLOADED` and `DOCUMENT_DELETED`.

## 9. Test document management and PDF

Continue using only fictitious documents.

1. Clear **Sertakan dalam PDF** on one optional image and confirm the readiness count changes.
2. Click **Putar 90°**, reload the page, and confirm both thumbnail and full preview retain the rotation.
3. Drag document cards into a new order, reload, and confirm the order remains unchanged. Also test **Lebih awal** and **Lebih akhir**.
4. Confirm **Buat PDF** remains unavailable until at least one Gambar USG is selected.
5. Click **Buat PDF**, verify the mandatory same-patient confirmation, then create the PDF.
6. Confirm the Drive filename follows `KLAIM_F1<KODE>_v001.pdf`, the file exists only in the private `OUTPUT` folder, and downloading through the app restores `KLAIM_<Puskesmas>_<YYYYMMDD>_<NIK>_<NO_HP>_v001.pdf`.
7. Confirm the PDF cover displays the complete 16-digit NIK, No. HP, and doctor name.
8. Use **Pratinjau PDF** and **Unduh PDF** from the web app. Confirm the staff account still cannot open the Drive file directly.
9. Create the PDF again and confirm version `v002` is created without overwriting `v001`.
10. Click **Selesaikan Klaim** and confirm upload, rotation, selection, ordering, deletion, and **Edit Data Klaim** are locked. A direct `updateClaim` request must return `CLAIM_REOPEN_REQUIRED`.
11. While still logged in as STAFF with access to the claim, click **Buka Kembali Klaim**. Confirm **Edit Data Klaim** becomes available only after the status changes to **Mengumpulkan berkas**, then change data or one document, regenerate the PDF, and complete the claim again. Confirm a staff user outside the claim's access boundary still cannot open or reopen it.
12. Review `AUDIT_LOG` for `DOCUMENT_SELECTION_UPDATED`, `DOCUMENT_ROTATED`, `DOCUMENTS_REORDERED`, `PDF_GENERATED`, `PDF_PREVIEWED`, `PDF_DOWNLOADED`, `CLAIM_COMPLETED`, and `CLAIM_REOPENED`.

If Google Docs conversion fails or requests authorization, sign in as the deploying administrator, approve the Google Documents scope, then retry. Do not grant staff direct access to the temporary document or output PDF.

The retained QR workflow is disabled by default. To enable it in the future, change `ENABLE_MOBILE_QR_UPLOAD` in `SETTINGS` to `true`, then reload the application. Leave it `false` for the single-Puskesmas workflow.

## 10. Test OrthancBridge

Follow [ORTHANC_BRIDGE.md](ORTHANC_BRIDGE.md) using fictitious DICOM data.

1. Create the bridge key from **Sistem** and confirm the **Orthanc** navigation is visible after the bridge is enabled.
2. Run `orthanc-bridge/run-once.ps1` on the Orthanc PC.
3. Confirm the examination appears as **Siap ditinjau** and that the claim has not yet been created.
4. Test NIK in `PatientID`, NIK in `PatientComments`, both fields empty, and conflicting 16-digit values. Confirm only one unique NIK is populated automatically.
5. Confirm the detected doctor name is shown when it is entered in either field and conflicting doctor names generate a warning.
6. Review all metadata, enter the No. HP manually, confirm or correct **Nama Dokter**, and select at least one image.
7. Confirm the patient and create the claim.
8. Confirm the claim opens as **Mengumpulkan berkas**, the selected USG images appear, and `DOCUMENTS.source_type` is `ORTHANC_IMPORT`.
9. Confirm each original `.dcm` instance exists in the claim's private `DICOM` folder and the Orthanc Study, Series, Instance, and frame identifiers are stored without appearing in public URLs.
10. Run the bridge again and confirm the same study is not duplicated.
11. Review `AUDIT_LOG` for `ORTHANC_STUDY_RECEIVED` and `ORTHANC_CLAIM_IMPORTED`.

Do not begin continuous synchronization until the one-time test has passed on the real Orthanc PC. Local automated tests do not prove connectivity to the clinic's Orthanc, Apps Script deployment, or DICOM codec compatibility.

## 11. Configure and test the second Drive account

1. In the approved backup account, create a private folder such as `BPJS_USG_BACKUP`.
2. Share only that folder as **Editor** with the Google account that owns/deploys the Apps Script web app. Do not enable link sharing.
3. Copy the folder ID from its Drive URL and add it in **Project Settings -> Script Properties** as `BACKUP_DRIVE_FOLDER_ID`.
4. Run `setupApplication()` again so the new schema and setting exist.
5. Run `validateSecondaryBackupConfiguration()` directly from the Apps Script editor and approve authorization if requested. It creates/validates private `DICOM RAW`, `DICOM`, and `KLAIM` subfolders and enables backup.
6. Run OrthancBridge without creating a claim and confirm every original file appears in `DICOM RAW` as `DICOM_RAW_F1<KODE>.dcm`.
7. Create a claim from a fictitious Orthanc study. Confirm the claim-linked files are named `DICOM_F1<KODE>[_NNN].dcm` in both the primary claim folder and backup `DICOM` folder.
8. Generate its PDF and confirm the second Drive contains `KLAIM_F1<KODE>.pdf`.
9. Regenerate the PDF and confirm the named backup is replaced by the latest version rather than duplicated.
10. Run **Sistem -> Jalankan Diagnostik** and confirm `Folder Drive cadangan` is `OK`.
11. Run `backupExistingClaimFiles()` repeatedly until `rawDicomReady`, `dicomReady`, and `pdfReady` are zero to anonymize and backfill existing files in bounded batches.
12. In the private Spreadsheet, verify each PDF/DICOM row contains the logical/original filename, anonymous storage filename, and its primary/backup Drive URL. Do not expose these URLs in the staff UI.

`setupApplication()` creates `FILENAME_CODE_SECRET` once. Never edit, rotate, or delete this property without a controlled migration because it determines the stable anonymous codes.

`F1` is one-way and cannot be decrypted. Preserve the private Spreadsheet mapping (`*_filename`, `*_storage_filename`, file ID, and Drive URL columns) together with the Drive data for recovery.

Do not paste the second account's password or credential JSON into Apps Script, `config.json`, chat, or Git. Folder-level sharing is sufficient for this design.

## 12. Configure and test the verifier Drive account

1. In the approved verifier account, create a private folder such as `BPJS_USG_VERIFIKATOR`.
2. Share only that folder as **Editor** with the Google account that owns/deploys the Apps Script web app. Do not enable link sharing and do not share the whole verifier Drive.
3. Copy the folder ID from its Drive URL and add it in **Project Settings -> Script Properties** as `VERIFIER_DRIVE_FOLDER_ID`. The folder must be different from `ROOT_DRIVE_FOLDER_ID` and `BACKUP_DRIVE_FOLDER_ID`.
4. Synchronize/deploy this source, then run `setupApplication()` once so the new `CLAIMS` columns and `ENABLE_VERIFIER_DRIVE_DELIVERY` setting exist.
5. Run `validateVerifierDriveConfiguration()` directly from the Apps Script editor. It validates write access to the configured parent folder, removes its temporary probe file, and enables delivery. It does not create an intermediate `KLAIM` folder.
6. Generate a PDF for a fictitious claim dated 3 October 2026. Confirm the application reports **PDF berhasil dikirim ke Drive verifikator** and the verifier parent contains `OKTOBER 2026/KLAIM_USG_PKM_<PUSKESMAS>_20261003_<NAMA_PASIEN>_<NIK>_DR_<NAMA_DOKTER>.pdf`.
7. Regenerate the PDF and confirm the previously tracked verifier copy is replaced by the new PDF without adding a version suffix. Confirm the primary claim `OUTPUT` folder still retains its normal `v001`, `v002`, and later versions.
8. In the private `CLAIMS` sheet, confirm `verifier_pdf_file_id`, logical/storage filenames, URL, timestamp, and `verifier_pdf_status=READY` are populated for the latest version. Do not expose the URL in the staff UI.
9. Run **Sistem -> Jalankan Diagnostik** and confirm `Folder Drive verifikator` is `OK`.
10. Test a controlled failure by temporarily removing Editor access, generate a fictitious PDF, and confirm the primary PDF remains available while the UI reports the verifier delivery failure. Restore Editor access and repeat with a new PDF version.

This feature sends PDFs generated after it is enabled. To rename and move the latest already-tracked verifier PDF for each claim directly into its examination-month folder, including files currently under `KLAIM/<BULAN>`, run `organizeExistingVerifierPdfFiles()` directly as `ADMIN_EMAIL`; it processes at most 100 files per run and may be run repeatedly while `hasMore` is `true`. The compatibility alias `renameExistingVerifierPdfFiles()` performs the same operation. Only the latest file ID tracked in each `CLAIMS` row is migrated; older untracked historical verifier copies and the old `KLAIM` folder are left unchanged for an administrator to review under the approved retention policy. The readable verifier filename and PDF body contain patient data, so the verifier folder must follow the approved clinical-data access and retention policy.

## 13. Configure and test Google Cloud Storage

1. Follow [GCS_DUAL_DELIVERY.md](GCS_DUAL_DELIVERY.md) to secure the service-account key and configure the Python bridge.
2. Run `setupApplication()` so `ENABLE_GCS_PDF_DELIVERY` and the `gcs_pdf_*` columns exist.
3. Add `GCS_BUCKET_NAME`, `GCS_OBJECT_PREFIX`, and `GCS_SERVICE_ACCOUNT_KEY` only in Script Properties.
4. Run `validateGcsConfiguration()` as `ADMIN_EMAIL`. Confirm its nonclinical probe is removed and the setting becomes `true`.
5. Create a fictitious claim, click **Buat PDF**, and confirm `gcs_pdf_status=WAITING_COMPLETION`; no claim PDF should exist in GCS yet.
6. Preview the result, then click **Selesaikan Klaim** only after it is correct. Confirm the UI reports GCS delivery, `gcs_pdf_status=READY`, and the anonymous `KLAIM_F1<KODE>_vNNN.pdf` object exists.
7. Run system diagnostics and confirm **Google Cloud Storage PDF** is `OK`.
8. Create a New version, update the deployment, and retest a fresh `/exec` URL before live operation.

If a completed claim records `gcs_pdf_status=ERROR`, correct the configuration and run `retryFailedGcsPdfDeliveries()` as `ADMIN_EMAIL`. It processes at most 100 `COMPLETED` claims per run and can be repeated while `hasMore` is `true`.

## Removing the unused Google OAuth configuration

After the password version works, the previous OAuth client and these obsolete Script Properties are no longer needed:

```text
GOOGLE_OAUTH_CLIENT_ID
GOOGLE_OAUTH_CLIENT_SECRET
OAUTH_REDIRECT_URI
```

Remove or disable the unused OAuth client in Google Cloud according to your administrator policy. Do not remove the new password properties.
