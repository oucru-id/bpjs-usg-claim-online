# Deployment with username and password

This version does not use Google OAuth for staff login. The web app still executes as the deploying administrator so the database Spreadsheet and Drive folders remain private.

## 1. Replace the Apps Script files

Copy all current files from `src/` to the Apps Script project.

Important:

- add `PasswordAuthService.gs`;
- add `ClaimService.gs` and `DriveService.gs`;
- add `DocumentService.gs`, `TokenService.gs`, and `VendorQrCode.html`;
- add `PdfService.gs`;
- add `OrthancBridgeService.gs`;
- delete the old `OAuthService.gs` from Apps Script;
- replace every other `.gs` and `.html` file;
- replace `appsscript.json`.

Enable **Project Settings → Show appsscript.json manifest file in editor** if the manifest is hidden.

## 2. Run the migration

Save all files, select `setupApplication`, and click **Run**.

Setup adds the `AUTH_CREDENTIALS` sheet and these Script Properties automatically:

```text
AUTH_MODE=USERNAME_PASSWORD
PASSWORD_PEPPER=<random secret generated by setup>
PASSWORD_HASH_ITERATIONS=12000
LOGIN_MAX_ATTEMPTS=5
LOGIN_LOCK_MINUTES=15
APP_SESSION_HOURS=8
```

Never delete or change `PASSWORD_PEPPER` after passwords have been created; doing so invalidates every password. Setup revokes sessions created by the previous authentication version. The obsolete `AUTH_IDENTITIES` sheet may remain but is no longer read.

For an existing installation, setup also adds the `must_change_password` column to `AUTH_CREDENTIALS`. If recognized columns are in an older order, setup safely rewrites them into the current order while preserving the values in every row. If an unknown, blank, or duplicate header exists, setup stops without modifying that sheet so the header can be reviewed manually.

If a recognized new column already contains data but its header is blank, setup repairs the header only when its position maps unambiguously to the expected column. Ambiguous blank columns still fail closed without changing data.

The new manifest requests Google Documents access because PDF composition uses a temporary private Google Doc. Review and approve this additional authorization when Google prompts the deploying administrator.

For version 5, setup also creates `ORTHANC_INBOX`, `ORTHANC_IMAGES`, the private `SYSTEM/ORTHANC_INBOX` folder, and the Orthanc reference columns on `DOCUMENTS`.

After a successful migration, the application header should display `5.0.0-orthanc-bridge`.

After deployment, log in as administrator, open **Sistem**, and run **Jalankan Diagnostik**. The server-side self-test function requires an application session token and is not intended to be run directly from the Apps Script editor.

## 3. Redeploy

1. Open **Deploy → Manage deployments**.
2. Edit the existing web-app deployment.
3. Select **New version**.
4. Keep **Execute as: Me**.
5. Set access to **Anyone**. Some interfaces describe this as anyone with the link.
6. Deploy and retain the production `/exec` URL.

The page is publicly reachable, but it returns no patient or account data until a valid application session is supplied. Every protected server function authorizes the session independently.

The `/exec` deployment also accepts authenticated outbound requests from OrthancBridge. Bridge reception remains disabled until an administrator generates a connection key. Continue with [ORTHANC_BRIDGE.md](ORTHANC_BRIDGE.md) only after the normal claim workflow passes its tests.

## 4. Create usernames and temporary passwords

Open `/exec` using the same Google account that owns/deploys the script. The installer administrator can enter without a password only to bootstrap account management.

1. Open **Pengguna**.
2. Edit each existing user.
3. Enter a unique username using 4-64 lowercase letters, numbers, dots, underscores, or hyphens.
4. Leave the password fields blank to use the default initial password `admin123`. If you enter a different temporary password, it must contain 6-128 characters.
5. Save. The account is marked as requiring a password change.
6. Finally, create a username for the Administrator account. This disables the installer-only bypass; the application will then require username/password login for everyone.

Examples of valid usernames:

```text
admin.bpjs
heri01
bidan_narmada
```

Do not reuse personal email, banking, or Google passwords.

## 5. Test staff login

1. Open the `/exec` URL in an incognito/private window.
2. Enter the staff username and `admin123` (or the temporary password entered by the administrator).
3. Confirm the application shows **Ganti Kata Sandi** instead of the dashboard.
4. Enter and confirm a new password of at least 6 characters. The new password cannot be `admin123`.
5. Confirm the dashboard loads without the Pengguna or Sistem admin menus.
6. Click **Keluar** and confirm the session is rejected afterward.
7. Enter an incorrect password five times and confirm login is temporarily blocked for 15 minutes.
8. Confirm the staff user still cannot open the private Spreadsheet or Drive folder.

Any password reset performed from **Pengguna** is temporary and forces the user through the same password-change screen.

## 6. Test user deletion

1. Create a temporary staff account that has never created or edited a claim or document.
2. Click **Hapus**, cancel once, and confirm the account remains.
3. Click **Hapus** again and confirm deletion.
4. Confirm the deleted username can no longer log in.
5. Confirm there is no **Hapus** button for your own current administrator account.
6. For a user referenced by claim or document history, confirm deletion is blocked and deactivate the account instead.

## 7. Test claim management

Use clearly fictitious data only, for example `Pasien Demo` and NIK `0000000000000000`.

1. Log in as STAFF and confirm all interface labels are in Bahasa Indonesia.
2. Click **+ Buat Klaim Baru**, enter the demo patient data, and save.
3. Confirm the generated code follows `CLAIM-YYYYMMDD-XXXXXX` and contains no patient name or NIK.
4. Confirm the list masks the patient name and NIK.
5. Open the claim and confirm the authorized detail displays the complete 16-digit NIK.
6. Edit it and select **Mulai Pengumpulan Berkas**.
7. Confirm a private folder named only with the claim code exists below the configured `CLAIMS` folder and contains the standard subfolders.
8. With a staff account from another facility, confirm the claim is not visible unless **Lihat semua klaim** was explicitly granted.
9. Log in as ADMIN, archive the demo claim, and confirm it disappears from the active list.
10. Enable **Sertakan arsip** and confirm the archived claim is searchable.
11. Review `AUDIT_LOG` for `CLAIM_CREATED`, `CLAIM_UPDATED`, `CLAIM_COLLECTION_STARTED`, and `CLAIM_ARCHIVED`.

## 8. Test image upload and mobile camera

Use only fictitious documents during this test.

1. Open a non-archived demo claim and upload two JPEG/PNG USG images from a computer.
2. Confirm both thumbnails appear and the Drive filenames contain only the document type and UUID.
3. Upload the same image again and confirm the duplicate warning appears.
4. Open the normal `/exec` URL on a phone and log in with an authorized application account.
5. Select the demo claim from **Daftar Klaim USG** and verify the patient, examination date, and facility.
6. From **Unggah Berkas Pendukung**, photograph one KTP, one Buku KIA page, and one SPP/FKPP BPJS document, waiting for each success message.
7. In the `DOCUMENTS` sheet, confirm each new supporting photo is at most 1280 x 720 in landscape or 720 x 1280 in portrait. Confirm its aspect ratio is not stretched.
8. Click **Perbarui Daftar** on the computer and confirm the new thumbnails appear.
9. Use **Lihat**, then delete one fictitious photo and confirm it disappears while its `DOCUMENTS` row remains with `deleted_flag=TRUE`.
10. Confirm another-facility staff account cannot find the claim or retrieve its thumbnails.
11. Review `AUDIT_LOG` for `DOCUMENT_UPLOADED` and `DOCUMENT_DELETED`.

## 9. Test document management and PDF

Continue using only fictitious documents.

1. Clear **Sertakan dalam PDF** on one optional image and confirm the readiness count changes.
2. Click **Putar 90°**, reload the page, and confirm both thumbnail and full preview retain the rotation.
3. Drag document cards into a new order, reload, and confirm the order remains unchanged. Also test **Lebih awal** and **Lebih akhir**.
4. Confirm **Buat PDF** remains unavailable until at least one Gambar USG is selected.
5. Click **Buat PDF**, verify the mandatory same-patient confirmation, then create the PDF.
6. Confirm the filename follows `BPJS_USG_CLAIM-..._v001.pdf` and the file exists only in the private `OUTPUT` folder.
7. Confirm the PDF cover displays the complete 16-digit NIK.
8. Use **Pratinjau PDF** and **Unduh PDF** from the web app. Confirm the staff account still cannot open the Drive file directly.
9. Create the PDF again and confirm version `v002` is created without overwriting `v001`.
10. Click **Selesaikan Klaim** and confirm upload, rotation, selection, ordering, and deletion are locked.
11. As ADMIN, click **Buka Kembali Klaim**, change one document, regenerate the PDF, and complete the claim again.
12. Review `AUDIT_LOG` for `DOCUMENT_SELECTION_UPDATED`, `DOCUMENT_ROTATED`, `DOCUMENTS_REORDERED`, `PDF_GENERATED`, `PDF_PREVIEWED`, `PDF_DOWNLOADED`, `CLAIM_COMPLETED`, and `CLAIM_REOPENED`.

If Google Docs conversion fails or requests authorization, sign in as the deploying administrator, approve the Google Documents scope, then retry. Do not grant staff direct access to the temporary document or output PDF.

The retained QR workflow is disabled by default. To enable it in the future, change `ENABLE_MOBILE_QR_UPLOAD` in `SETTINGS` to `true`, then reload the application. Leave it `false` for the single-Puskesmas workflow.

## 10. Test OrthancBridge

Follow [ORTHANC_BRIDGE.md](ORTHANC_BRIDGE.md) using fictitious DICOM data.

1. Create the bridge key from **Sistem** and confirm the **Orthanc** navigation is visible after the bridge is enabled.
2. Run `orthanc-bridge/run-once.ps1` on the Orthanc PC.
3. Confirm the examination appears as **Siap ditinjau** and that the claim has not yet been created.
4. Confirm a non-16-digit `PatientID` does not automatically populate NIK.
5. Review all metadata and select at least one image.
6. Confirm the patient and create the claim.
7. Confirm the claim opens as **Mengumpulkan berkas**, the selected USG images appear, and `DOCUMENTS.source_type` is `ORTHANC_IMPORT`.
8. Confirm the Orthanc Study, Series, Instance, and frame identifiers are stored without appearing in public URLs or filenames.
9. Run the bridge again and confirm the same study is not duplicated.
10. Review `AUDIT_LOG` for `ORTHANC_STUDY_RECEIVED` and `ORTHANC_CLAIM_IMPORTED`.

Do not begin continuous synchronization until the one-time test has passed on the real Orthanc PC. Local automated tests do not prove connectivity to the clinic's Orthanc, Apps Script deployment, or DICOM codec compatibility.

## Removing the unused Google OAuth configuration

After the password version works, the previous OAuth client and these obsolete Script Properties are no longer needed:

```text
GOOGLE_OAUTH_CLIENT_ID
GOOGLE_OAUTH_CLIENT_SECRET
OAUTH_REDIRECT_URI
```

Remove or disable the unused OAuth client in Google Cloud according to your administrator policy. Do not remove the new password properties.
